# Buildto V2.1 — Eight-gap implementation contract

**Scope**: production-target database model with safety constraints. These constraints are not equivalent to a complete production application; the backend must follow the protocols below. Current Neon untouched.

## 1. Shipment OTP / site handover

Shipment stores the **HMAC-SHA256 digest** of a server-generated random 6-digit PIN (the hex digest), issuance, expiry, verified timestamp, bounded attempt counter and lockout. A plain SHA256 over six digits is guessable offline; use a distinct server-held secret per environment and include shipment ID/nonce in HMAC input. Never store/log/plaintext the PIN or deliver it to the supplier actor that performs verification. Send the PIN to the authenticated site contact over a controlled channel. OTP validity should be short-lived and enforced with one atomic API transaction (row lock + attempt increment + expiry check + HMAC constant-time comparison + single-use verification). DB ensures only verified or privileged exception-approved shipments can be fully DELIVERED. Avoid storing OTPs in screenshots/media. Exception requires reason, approver and an audit event plus photo/site evidence; backend must authorize approver independently from the courier. Handle partial deliveries and signature/receipt disputes separately.

## 2. Supplier-collected COD

`CodCollection` tracks physical cash under `SupplierOrder` (optionally one shipment), receipt, collector, verifier, idempotency and posted journal reference. Atomic counters on SupplierOrder prevent multiple receipts summing beyond the order amount. `SupplierCommissionReceivable` tracks platform commission to be offset against payouts or invoiced. COD is NOT digital gateway capture. Do not set paid based merely on the courier entering a number. A verifier must confirm receipt, a balanced journal must be posted, and settlement accounting must reflect supplier-held cash. Every reversal uses compensating journal and audit events; do not silently edit verified receipts. Collection/receipt identity and ID/payment authorization are server-checked, and physical cash processes require finance ops approval.

## 3. Geospatial serviceability

`ServiceArea.geoCenter` and `geoBoundary` are PostGIS geography fields (Prisma 5.22 `Unsupported`), synchronized from lat/lng by SQL for geoCenter. `CREATE EXTENSION IF NOT EXISTS postgis` is a prerequisite. GiST indexes support `ST_DWithin` and polygon containment (not instant guaranteed queries). Use supplier area eligibility, verified center + radius or approved polygon, dimensional cargo restrictions, time windows and city/PIN code as additional filters; do not use PIN code alone as radial proof. Lat/lng data must be validated; map/address points should be geocoded and sourced from verified coordinates. Use prepared/parameterized SQL for raw spatial operations and test explain plans at representative volume.

## 4. BigInt wire contract

Every monetary `*Paise` field is represented as a **decimal string on the REST API** (even if small). Use explicit, allowlisted API DTO mapping with `api/json-safe.mjs` as serializer; do not patch global `BigInt.prototype`. Keep exact `Decimal` unit prices/quantities as decimal strings. Mobile/web clients use decimal math/BigInt or decimal libraries and do not round through JavaScript Number. This does not automatically filter secrets from raw database rows.

## 5. Multi-truck/partial shipment safeguards

`SupplierOrderItem.allocatedShipmentQty` is maintained by database triggers using a conditional `UPDATE` of a single order-item row for each insert/update/delete of ShipmentItem. It never exceeds purchased quantity, even with multiple concurrent truck assignments. Terminal shipment statuses (CANCELLED, FAILED, RETURNED) release allocation and reactivation reacquires it. Immutable ownership of a shipment line prevents transfer loopholes. Per-line delivered/rejected/returned quantities are bounded. Backend transactions must use deterministic lock order for multi-line shipments; retry deadlocks and ensure status-transition authorization, shipment-event history and actual inventory movements. Write hostile concurrent tests beyond the serial smoke suite.

## 6. Indian GST

`Supplier.gstRegistration` distinguishes REGULAR, COMPOSITION, UNREGISTERED, EXEMPT and UNVERIFIED. SupplierOrderItem and TaxInvoice store exact CGST, SGST, UTGST, IGST and optional cess components; SQL ensures components sum to tax. Composition/unregistered sellers cannot issue a taxable `TAX_INVOICE`; bill of supply has no charged GST. Service validates place of supply, seller/buyer registration, GSTIN, HSN/SAC, tax rates and seller snapshot, and creates legally appropriate tax documents. **Consult an Indian tax professional** before relying on this for statutory compliance; there are subtleties around mixed rates, reverse charge, composition regimes, cess and credit notes.

## 7. Cargo-aware supplier rates

SupplierDeliveryRate supports base/per-km/weight-distance/volume-distance amounts, vehicle capacities and optional vehicle class. SupplierFreightBracket selects a configured weight or volume range with fee + distance multipliers, with an exclusion rule preventing overlapping active tiers per rate/dimension. Total order weight/volume derives from verified product specs and pack conversions; reject or RFQ freight quotes with missing physical dimensions or vehicle capacity. Enforce minimum/full truck rates, multi-trip charges, handling and unloading at quote time. Each placed order snapshots the accepted freight quote.

## 8. Partial cancellations

`PurchaseOrderStatus.PARTIALLY_CANCELLED` is derived from independently statused supplier orders. The database trigger updates parent state on each child status change, preserving other supplier orders. Backend owns child cancellation eligibility, status events, inventory reservation release, refunds, commission adjustment, delivery cancellation and customer notification per supplier. Never cancel or refund sibling supplier orders automatically. Parent `CLOSED` is a terminal business closure and intentionally not reopened by the status derivation trigger.

## Source code caution

The API/Flutter code in main and the former demo branch still target the **legacy** schema. Do not merge the V2.1 target contract into `backend/prisma/schema.prisma` or run migration SQL on a populated Neon branch without a compatibility and backfill implementation.
